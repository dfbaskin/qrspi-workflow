# Cross-tool QRSPI AI Coding Workflow Implementation

## Overview

QRSPI is a staged workflow for non-trivial coding tasks. Eight user-invoked phases, each writing one
markdown artifact that the next phase reads instead of re-deriving context. The phases exist to
separate *what exists* from *what we want* from *how we get there*.

| Skill | Produces | Purpose |
|---|---|---|
| `qrspi-1-question` | `task.md`, `questions.md` | Decompose the task into 3-7 neutral research questions |
| `qrspi-2-research` | `research.md` | Answer them from the codebase — facts and `file:line` refs only |
| `qrspi-3-design` | `design.md` | Agree on the destination and the decisions behind it |
| `qrspi-4-structure` | `structure.md` | Break the design into vertical, independently testable slices |
| `qrspi-5-plan` | `plan.md` | Expand the slices into a self-contained implementation plan |
| `qrspi-6-worktree` | a git worktree | *Optional* — isolate the work on its own branch |
| `qrspi-7-implement` | code, one commit per phase | Execute the plan, verifying at each checkpoint |
| `qrspi-8-pr` | a pull request | Open the PR with the reasoning inlined |

The artifacts are the compaction. You review ~200 lines of research and ~200 lines of plan rather
than 2,000 lines of diff, and the approval gates land at the points where changing direction is
still cheap. Phase 2 runs deliberately blind to the task description so its findings stay
objective — that isolation is the whole reason the phases are separate rather than one long prompt.
See [`.ruler/AGENTS.md`](.ruler/AGENTS.md) for the artifact layout and the invocation rules.
(Of course, it's highly recommended to read the code as well!)

What this repo adds: upstream ships QRSPI as Claude Code slash commands. Here the same eight phases
are restated as **skills**, and [ruler](https://github.com/intellectronica/ruler) generates the
equivalent layout for Claude Code, Cursor, GitHub Copilot, Codex CLI and Gemini CLI from one
hand-authored source in `.ruler/`.

## Install

Grab the archive for your tool from the [latest release](../../releases/latest), verify it, and
unzip it at the root of your repository:

```bash
sha256sum -c qrspi-claude-1.0.0.zip.sha256 && unzip -o qrspi-claude-1.0.0.zip
```

| Bundle | Tool | Contents |
|---|---|---|
| `qrspi-claude-<version>.zip` | Claude Code | `CLAUDE.md`, `.claude/skills/`, `.claude/agents/` |
| `qrspi-cursor-<version>.zip` | Cursor | `AGENTS.md`, `.cursor/skills/`, `.cursor/agents/` |
| `qrspi-copilot-<version>.zip` | GitHub Copilot | `AGENTS.md`, `.claude/skills/`, `.github/agents/` |
| `qrspi-codex-<version>.zip` | Codex CLI | `AGENTS.md`, `.agents/skills/`, `.codex/agents/` |
| `qrspi-gemini-cli-<version>.zip` | Gemini CLI | `AGENTS.md`, `.gemini/settings.json`, `.gemini/skills/` |

Cursor, Copilot, Codex and Gemini all read the same root `AGENTS.md`, and Copilot reads its skills
from `.claude/skills/` — both are ruler's layout, not a packaging mistake.

## Contributing

`.ruler/` is the only hand-authored source: one `AGENTS.md`, eight skills, four subagents.
Everything else in the tree is generated by [ruler](https://github.com/intellectronica/ruler) and
gitignored.

```bash
pnpm install && pnpm run ruler:apply
```

See [`CONTRIBUTING.md`](CONTRIBUTING.md) for the repo layout, the skill conventions, and how
releases are cut.

## Why only the workflow

This repo extracts the QRSPI prompts and nothing else, on purpose. Isolating them makes it cheap to
answer one question: *does the staged-artifact methodology actually pay off on our codebases?* You
get that answer without adopting a new IDE, changing where sessions run, or asking a team to move
onto a platform. It is files in a repo — `git rm` them and you are back where you started.

The corollary is that what you get here is only the methodology. There is no session orchestration,
no artifact versioning, no shared review surface, no multi-repo worktree management. Those are real
parts of the problem, and this repo does not address them.

If the workflow proves itself, go look at [HumanLayer](https://humanlayer.com) — their tool covers
the parts that loose files in a repo cannot:

- Task workspaces that group agent sessions, artifacts and worktrees together
- Its own QRSPI phases, maintained by the people who developed the methodology
- Real-time collaboration — teammates and agents commenting on the design document *before*
  implementation, which is exactly where QRSPI's approval gates want to live
- Multi-repo worktree management
- Local and cloud daemons, so sessions run on your laptop or on cloud infrastructure
- Bring-your-own-key against an existing Claude or Codex subscription

Their RPI framework is open source; the wider product is not yet.

Thank you to the team at **[HumanLayer](https://humanlayer.com)**, whose work on context engineering
for coding agents is what this workflow rests on:

- [Advanced Context Engineering for Coding
  Agents](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents) — Dex
  Horthy's write-up of intentional compaction and the Research-Plan-Implement loop (`ace-fca.md`).
  They report fixing a bug in a ~300k-line Rust codebase in about an hour with the PR accepted
  upstream, and shipping ~35k lines in a single seven-hour session, working at a deliberate 40-60%
  context utilization.
- [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) — the agent design principles
  behind how each phase is scoped.

HumanLayer has since evolved RPI into a QRSPI framing inside their own product.

the cross-tool packaging, not the methodology.
